## 一、先让数据库查得快、存得对

### 1. 数据库索引：给查询建立一条更短的查找路径

**是什么**：索引是一种帮助数据库定位数据的结构。常见 B-tree 索引适合等值、范围和有序访问，但数据库不一定每次都选择它。

**Java 场景**：订单列表经常按用户筛选，再按时间倒序分页：

```sql
CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at DESC);

SELECT id, created_at, total_amount
FROM orders
WHERE user_id = :userId
ORDER BY created_at DESC
LIMIT 20;
```

Spring Data JPA 或 MyBatis 只是执行查询；真正决定查询路径的是数据库。联合索引的列顺序应匹配过滤、排序和实际数据分布，不能只按 Java 实体字段排列。

**容易踩坑**：索引会占空间，也会增加写入和维护成本。不是每列都建索引就会更快；对索引列做函数运算、隐式类型转换，也可能影响索引使用。

### 2. 查询优化：先减少工作量，再考虑加机器

**是什么**：让数据库以更少的扫描、连接、排序和数据传输完成同一项业务查询。

**Java 场景**：列表只显示订单号和金额，就用 DTO 投影获取所需列；避免先查出全部订单，再在 Java Stream 中筛选或分页。深分页时，可以考虑游标式分页：

```sql
SELECT id, created_at, total_amount
FROM orders
WHERE user_id = :userId
  AND (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

这类查询应评估 `(user_id, created_at DESC, id DESC)` 索引，第一页则不带游标条件。`id` 用来处理多条订单时间相同的情况。

**容易踩坑**：不要凭 SQL 长短判断性能。先找慢查询，再看执行计划、返回行数与延迟，比较优化前后结果是否一致。

### 3. EXPLAIN ANALYZE：看看数据库实际上怎么执行

**是什么**：`EXPLAIN` 展示执行计划；在 PostgreSQL 中，加上 `ANALYZE` 会真正执行语句，提供实际耗时、行数和循环次数。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM orders WHERE user_id = 42;
```

**Java 场景**：从 JPA/MyBatis 日志中提取实际 SQL 和有代表性的绑定值，在合适的测试环境检查。重点看预估行数与实际行数是否偏离、是否发生大量扫描和排序、嵌套循环执行了多少次。

**容易踩坑**：`EXPLAIN ANALYZE UPDATE ...` 会真的更新数据。回滚也不能消除所有外部副作用或执行成本；生产排查要先确认语句类型、负载和操作边界。不同数据库的语法与指标也不完全一样。

### 4. N+1 查询：一段循环，悄悄变成上百次数据库往返

**是什么**：先查一次主列表，再对每条记录额外查询一次关联数据。查 100 个订单，可能变成 1 + 100 次查询。

```java
// 反例：customer 为懒加载关联时，访问它可能触发额外查询
for (Order order : orderRepository.findAll()) {
    System.out.println(order.getCustomer().getName());
}
```

**怎么处理**：按页面需要使用 DTO 投影、`JOIN FETCH`、`@EntityGraph` 或批量加载。需要分页且关联一对多集合时，常用做法是先分页查订单 ID，再批量查关联数据。

**容易踩坑**：全部改成 `EAGER` 并不保证只有一条 SQL。对一对多集合直接 fetch join 再分页，还可能导致结果膨胀或内存分页。要用实际 SQL 数量和返回数据验证。

### 5. 唯一约束：让数据库守住“只能有一个”

**是什么**：由数据库保证某个列或列组合不出现重复值。

```sql
ALTER TABLE orders
ADD CONSTRAINT uq_orders_user_request UNIQUE (user_id, request_id);
```

**Java 场景**：客户端重复提交同一笔下单请求时，用用户 ID 和请求 ID 标识一次业务操作。应用可以先查，但并发下最终仍依靠唯一约束裁决；同时应将相关字段设为 `NOT NULL`。

**容易踩坑**：“先查不存在，再插入”存在竞态。JPA 的约束错误可能在 flush 或提交时才出现，异常后的事务也可能不能继续使用；不要在同一个已失败事务里直接查询旧结果。可以在事务边界外处理冲突，再开启新事务读取。

### 6. 外键约束：保证引用的数据确实存在

**是什么**：例如 `order_items.order_id` 必须指向一条存在的订单，防止出现没有所属订单的明细。

```sql
ALTER TABLE order_items
ADD CONSTRAINT fk_order_items_order
FOREIGN KEY (order_id) REFERENCES orders(id);
```

**Java 场景**：JPA 的 `@ManyToOne` 描述对象关系；数据库是否真的有外键，要看迁移脚本和实际表结构。删除订单时，应明确是限制删除、级联删除还是采用业务上的软删除。

**容易踩坑**：不要认为“Java 代码校验过”就永远不会有脏数据。脚本、并发和其他服务都可能绕开校验。跨独立数据库通常不能靠普通外键保证一致，需要另外设计。

### 7. 数据库分区：把一张逻辑表拆成多个存储分区

**是什么**：按时间、范围、列表或哈希等规则，把同一张逻辑表的数据组织到不同分区。常见用途是管理大表和历史数据。

**Java 场景**：订单按月份分区，Java 仍查询 `orders`。查询带上时间范围，数据库才更有机会通过分区裁剪跳过无关分区。

**容易踩坑**：分区不等于分布到多台数据库，也不保证任何查询都更快。分区表的唯一约束、索引和外键支持有产品限制，应先确认；按时间删除历史数据时也要考虑归档与引用关系。

### 8. 数据库分片：把数据分散到不同数据库节点

**是什么**：例如按 `user_id` 把不同用户的订单放到不同数据库，分摊存储与读写压力。

**Java 场景**：可以由应用路由或 ShardingSphere 等组件选择数据源。设计时要先回答：查询有没有分片键？跨分片分页怎么办？扩容时怎样迁移？

**容易踩坑**：`userId % 4` 很容易写出来，但从 4 片扩到 8 片会影响大量路由。跨分片 JOIN、全局唯一性和事务都更复杂。通常先评估索引、归档、缓存和读扩展，再决定是否分片。

## 二、并发请求下，怎样把一次业务做正确

### 9. 竞态条件：结果取决于多个操作如何交错

**是什么**：多个请求访问同一份状态，正确性又依赖执行顺序，却没有合适的协调机制。

**Java 场景**：库存为 1，两个线程都先读到 1，再各自写回 0，最后卖出两件。即使读写各自成功，组合起来仍然错误。

```sql
UPDATE products
SET stock = stock - :quantity
WHERE id = :id AND stock >= :quantity;
```

当 `quantity > 0` 时，Java 根据更新行数判断扣减是否成功。把条件与修改放进一条原子语句，可以避免这种“先查后改”的竞争；订单写入仍需放进同一业务事务。

**容易踩坑**：`synchronized` 只协调同一个 JVM 内、共享同一把锁的线程。服务部署成多个实例后，它不能保护所有实例共同访问的数据库。

### 10. 数据库事务：把一组数据库操作作为一个提交单元

**是什么**：下单时扣库存成功、写订单失败，就应撤销本次扣减，而不是留下一半结果。

```java
@Service
public class OrderService {
    @Transactional(rollbackFor = Exception.class)
    public Long placeOrder(CreateOrderCommand command) {
        int changed = productRepository.decreaseIfEnough(
            command.productId(), command.quantity());
        if (changed != 1) {
            throw new IllegalStateException("库存不足");
        }
        return orderRepository.insert(command);
    }
}
```

这里假设参数已校验、两个 Repository 使用同一个事务管理器下的数据库连接，并且由其他 Bean 通过 Spring 代理调用此方法。

**容易踩坑**：Spring 常见代理模式下，同类内部直接调用不会经过事务代理。默认回滚规则主要针对 `RuntimeException` 和 `Error`；吞掉异常也可能导致提交。事务还不会自动撤销已经发出的 HTTP 请求或普通 MQ 消息。

### 11. ACID 属性：事务提供的四类保证

| 属性 | 含义 | 下单例子 |
| --- | --- | --- |
| Atomicity，原子性 | 事务内修改全部提交或全部回滚 | 扣库存与写订单共同成功 |
| Consistency，一致性 | 从一个满足约束的有效状态转到另一个 | 余额、库存符合已定义的规则 |
| Isolation，隔离性 | 约束并发事务之间的相互影响 | 两个下单请求按所需隔离规则运行 |
| Durability，持久性 | 提交后在承诺的故障范围内保留结果 | 数据库恢复后仍能找到已提交订单 |

**Java 场景**：`@Transactional` 帮助划定边界，数据库实现具体保证。

**容易踩坑**：ACID 的 C 不等于分布式副本立即一致；数据库也不会替你猜出所有业务规则。持久性还受日志刷盘、复制和故障切换配置影响。

### 12. 隔离级别：允许并发事务看见什么、互相影响到什么程度

**是什么**：常见名称有读未提交、读已提交、可重复读和可串行化。脏读是读到未提交数据，不可重复读是同一行重复读取发生变化，幻读涉及符合条件的行集合变化。

**Java 场景**：可通过 `@Transactional(isolation = Isolation.READ_COMMITTED)` 表达需求，但数据库必须支持，且方法若加入已有事务，不一定会改变外层事务的隔离级别。

**容易踩坑**：不能只背一张通用异常对照表。PostgreSQL 的读未提交按读已提交处理；PostgreSQL 与 MySQL InnoDB 的可重复读机制也有差异。普通快照读、锁定读和写操作的行为需要分别理解。可串行化也可能通过中止事务来保证正确性，应用必须处理重试。

### 13. 乐观锁：提交修改时检查状态有没有变过

**是什么**：读取时不一直持有排他锁，更新时校验版本；版本已变化就报告冲突。

```java
@Version
private long version;
```

JPA 管理的版本字段通常让更新包含类似条件：

```sql
UPDATE products
SET stock = :newStock, version = version + 1
WHERE id = :id AND version = :oldVersion;
```

**Java 场景**：冲突相对少、允许重新读取后再计算的业务。更新失败时通常要回滚当前事务，在新的事务中重新执行完整业务判断。

**容易踩坑**：乐观锁并不是数据库执行时完全不加锁。高竞争下反复失败与重试可能降低吞吐；批量 JPQL 或原生 SQL 也不能想当然地认为会自动遵循实体版本逻辑。

### 14. 悲观锁：先锁住需要协调的数据，再操作

**是什么**：读取时就获取数据库锁，让竞争者等待或失败。

```sql
BEGIN;
SELECT stock FROM products WHERE id = :id FOR UPDATE;
-- 校验库存，扣减库存，写订单
COMMIT;
```

**Java 场景**：在事务内使用 JPA 的 `PESSIMISTIC_WRITE` 或 MyBatis 的锁定 SQL。适合冲突较多、必须围绕当前状态做多步判断的场景。

**容易踩坑**：拿着数据库锁调用慢速第三方接口，会拉长等待并占用连接。查询索引、隔离级别和数据库实现会影响实际锁范围，并不是永远只锁住你想象中的那一行。

### 15. 死锁：大家互相等对方释放资源

**是什么**：事务 A 锁住商品 1 等商品 2，事务 B 锁住商品 2 等商品 1，形成等待环。

**Java 场景**：一个订单涉及多个商品时，先按商品 ID 排序，再统一顺序扣减；缩短事务时间，检查执行计划和锁等待。

**容易踩坑**：死锁不只发生在显式 `FOR UPDATE`，普通更新、索引和外键检查也可能参与。数据库通常会中止其中一个事务；重试应在新事务中重新执行完整操作，并满足幂等要求，不能只重放最后一条 SQL。

### 16. 幂等性：同一个业务操作重复执行，效果仍只发生一次

**是什么**：请求可以重复到达，但不能因此多扣一次款、多建一张订单。

**Java 场景**：客户端为一次下单生成 `requestId`，服务端记录请求指纹、处理状态与最终结果，并用唯一约束防并发重复。同一个键但请求内容不同，应拒绝或报告冲突；处理中的请求也要有明确语义。

支付回调还可以使用条件状态迁移：

```sql
UPDATE orders SET status = 'PAID'
WHERE id = :id AND status = 'UNPAID';
```

只有状态真正改变的事务才记录后续待办事件；订单金额、币种和支付归属也必须先校验。

**容易踩坑**：Redis `SET NX` 只是一个协调手段，单独使用不能解决进程崩溃、锁过期或数据库提交后的重试。幂等记录应与受保护的业务写入建立可靠的原子关系。

## 三、缓存提高速度，也会带来一致性问题

### 17. 分布式缓存：多个服务实例共享一份缓存

**是什么**：把常用数据放到 Redis 等独立服务，让多个 Java 实例共同使用。Caffeine 则是常见的 JVM 本地缓存。

**Java 场景**：商品详情先查 Redis，未命中再查数据库并回填，这叫 cache-aside。Spring Cache 可以简化调用，但需要显式配置缓存管理器、序列化、键和 TTL。

**容易踩坑**：分布式缓存增加了网络依赖，也会故障；本地缓存又有多实例数据不一致的问题。缓存命中率高也不能替代数据库约束，不能用缓存库存读数直接裁决扣减。

### 18. 缓存失效：何时不再相信旧值

**是什么**：数据库变化后，让缓存中的旧值过期、删除或被新值替换。

**Java 场景**：常见策略是提交数据库事务后删除相关缓存，再以 TTL 限制旧值存活时间。使用 Spring 事务时，应明确失效动作发生在提交之后，可通过事务事件等机制组织。

**容易踩坑**：“更新数据库，再删缓存”仍有删除失败与并发旧值回填的窗口；`@CacheEvict` 也不应被想当然地当作提交后执行的保证。严格要求下要加入可靠失效事件、版本控制或绕过缓存读关键数据。延迟双删只能缓解某些时序问题，不能普遍保证强一致。

### 19. 缓存踩踏：缓存一失效，大量请求同时回源

**是什么**：热点键过期或一批键集中失效时，许多请求一起访问数据库，造成负载突增。前者常被称为缓存击穿，大范围失效也常被称为缓存雪崩。

**Java 场景**：对同一个键合并并发加载；允许旧值短暂服务并在后台刷新；为 TTL 加随机偏移；同时限制回源并发。

**容易踩坑**：单 JVM 的互斥只合并该实例内的请求。使用跨实例锁时，要考虑租约过期、持有者校验和加载失败。查不存在的数据导致反复回源是另一类问题，常叫缓存穿透，可考虑短期负缓存或布隆过滤器。

### 20. Redis 淘汰策略：内存不够时先移走谁

**是什么**：达到 `maxmemory` 后，Redis 根据策略尝试淘汰键。它与 TTL 到期删除是两种机制。

| 策略 | 大致行为 |
| --- | --- |
| `noeviction` | 不淘汰，可能增加内存的写入会报错 |
| `allkeys-lru` | 在所有键中近似淘汰最近较少使用的键 |
| `allkeys-lfu` | 在所有键中近似淘汰访问频率较低的键 |
| `volatile-lru` | 只在设置了过期时间的键中做近似 LRU 淘汰 |

**Java 场景**：缓存用途可根据负载评估 LRU 或 LFU；应用必须把未命中当作正常情况。

**容易踩坑**：不能把随时允许淘汰的商品缓存，与依赖保留的幂等记录、锁状态等混在一起却忽略淘汰风险。`noeviction` 也不等于可靠持久化，数据可靠性还要另行设计。

### 21. 抖动：给时间安排加入随机性

**是什么**：这里的 jitter 指有意添加随机偏移，打散大量客户端同时发生的行为，不是泛指网络不稳定。

```java
long ttlSeconds = 300 + ThreadLocalRandom.current().nextLong(61);
```

**Java 场景**：给缓存 TTL 加 0～60 秒偏移，也可给重试等待、定时刷新加入随机性。

**容易踩坑**：随机过期时间不能阻止某一个超级热点键过期时被同时访问。它需要与请求合并、后台刷新或限流配合。

## 四、消息与后台任务：把耗时工作可靠地移出去

### 22. 消息队列：让生产者与消费者通过消息协作

**是什么**：订单服务发送“订单已创建”事件，库存通知、积分等消费者按自己的速度处理。常见产品有 RabbitMQ、Kafka、RocketMQ，但投递和消费语义不同。

**Java 场景**：Spring AMQP 或 Spring Kafka 可以提供发送和监听接口。消费者应在业务结果持久化后，再按所选产品的语义确认或提交消费位置。

**容易踩坑**：发送成功不代表业务已消费成功。许多可靠配置提供至少一次投递，因此重复消息是必须处理的正常情况；顺序通常也只在特定队列或分区范围内成立。

### 23. 后台工作者：专门处理异步任务的执行者

**是什么**：worker 从队列或任务表获取工作，完成邮件发送、图片处理、报表导出等操作。

**Java 场景**：一个独立 Spring Boot worker 监听队列，限制并发数，处理成功后确认；失败则按规则重试或进入死信。

**容易踩坑**：`@Async` 通常只是把工作交给当前进程的线程池，进程退出可能丢失尚未完成的任务。需要可靠执行时，要有持久任务来源、失败记录和崩溃恢复机制。

### 24. 作业调度：决定任务什么时候启动

**是什么**：如每天生成账单、每隔五分钟清理超时订单。调度负责触发，worker 负责执行，两者可以分开。

**Java 场景**：简单任务可以使用 `@Scheduled`；需要持久化、集群协调或补偿调度时，可评估 Quartz、XXL-JOB 等方案。

**容易踩坑**：应用有三个实例，普通 `@Scheduled` 可能触发三次。还要定义时区、错过触发时间怎么办、上次任务未完成是否允许重叠。集群协调不能替代业务幂等。

### 25. 死信队列：给暂时无法正常处理的消息一个去处

**是什么**：超过重试上限或满足特定拒绝、过期规则后，把消息送到独立队列或主题，供排查与补偿。具体机制依产品而异。

**Java 场景**：消费者遇到格式错误、业务数据缺失等问题，记录原始消息标识、失败原因、次数与时间，再按策略转入 DLQ。

**容易踩坑**：死信队列不是自动恢复工具。必须有告警、保留期限、排查流程和可控重放；重放时仍要幂等，也不能把永久错误无限扔回主队列。

### 26. 出站模式：用事务性发件箱解决数据库与消息的双写问题

**是什么**：这里将清单中的“出站模式”按常见后端语境理解为 Transactional Outbox，也常译为“事务性发件箱”。订单和待发送事件写进同一个数据库事务，再由投递器发送事件。

```java
@Transactional
public void createOrder(CreateOrderCommand command) {
    Long orderId = orderRepository.insert(command);
    outboxRepository.insert(UUID.randomUUID(), "OrderCreated", orderId);
}
```

**Java 场景**：后台投递器轮询 outbox 表，或由 CDC 捕获变更，成功投递后更新状态。事件需保存足够的载荷或版本信息，避免稍后读取到已变化的业务状态。

**容易踩坑**：消息发出后、标记成功前进程崩溃，会再次发送。Outbox 解决可靠衔接问题，并不自动提供端到端 exactly-once；消费者仍需用事件 ID 去重，多投递器还需协调领取和顺序。

![事务性发件箱流程：订单与 Outbox 同事务提交，投递器发送到队列，消费者按事件 ID 去重](/images/java-backend-50/transactional-outbox.svg)

*图 2：本地事务保证订单和待发送事件共同落库；消息投递与消费仍要处理重复。*

### 27. Webhook 验证：确认通知确实来自可信发送方

**是什么**：Webhook 是第三方主动发来的 HTTP 回调，必须验证来源与内容完整性，再执行业务。

**Java 场景**：支付平台常要求按协议用 HMAC-SHA256 计算签名。下面只演示“平台规定对时间戳、点号和原始 body 签名”的情形：

```java
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(new SecretKeySpec(secretBytes, "HmacSHA256"));
mac.update((timestamp + ".").getBytes(StandardCharsets.UTF_8));
byte[] expected = mac.doFinal(rawBody);
boolean valid = MessageDigest.isEqual(expected, decodedSignature);
```

实际应按平台协议解析签名、编码与密钥版本；校验签名后，还要检查时间戳容差、事件 ID、订单归属、金额和币种。对重复事件做幂等处理。

**容易踩坑**：不要先解析 JSON 再序列化来验签，空格、字段顺序变化可能改变字节。签名只能证明消息按协议经过认证，不代表消息尚未处理；过期与重放要另外防范。

### 28. Webhook 重试：双方协作，允许通知暂时失败

**是什么**：发送方收到失败响应或发生超时后，按约定重新投递。接收方必须接受通知可能重复、延迟或乱序。

**Java 场景**：接收端验签后，将事件可靠写入 inbox 表或持久队列，再返回平台约定的成功状态码；worker 后续处理。发送端则记录投递状态、次数、下次投递时间和最终失败原因。

**容易踩坑**：返回成功后才开始尝试持久化，可能在崩溃时丢事件。对方业务已成功但响应丢失时，重试又会制造重复。不同平台如何解释 4xx、5xx 和成功码并不相同，要遵守其协议。

## 五、失败不可避免，关键是别把失败放大

### 29. 重试机制：给暂时性失败一次恢复机会

**是什么**：网络抖动、临时不可用等问题可能稍后恢复，重新调用有机会成功。

**Java 场景**：用 Resilience4j 或 Spring Retry 对明确可恢复的错误执行有限次重试，配置单次超时、总截止时间和取消机制。

**容易踩坑**：参数错误、鉴权失败通常不应盲目重试。超时也不等于对方没执行；重试扣款等操作前必须有幂等设计。网关、服务、SDK 每层都重试会成倍放大流量，应统一重试预算与责任层。

### 30. 指数退避：越失败，等得越久

**是什么**：按 100ms、200ms、400ms 等增长等待时间，直到上限，避免故障期间持续猛打下游。

常见 full jitter 形式：`等待时间 = random(0, min(上限, 基础时间 × 2^重试序号))`，序号从 0 开始。

```java
long capMs = 5_000;
long baseMs = 100;
int exponent = Math.min(retryIndex, 6); // retryIndex >= 0
long ceilingMs = Math.min(capMs, baseMs * (1L << exponent));
long delayMs = ThreadLocalRandom.current().nextLong(ceilingMs + 1);
```

**Java 场景**：通过调度器或重试库安排下一次调用，不要在 Web 请求线程里长时间 `sleep`。若服务提供 `Retry-After`，应结合协议与剩余请求预算处理。

**容易踩坑**：只加退避却不限制尝试次数和总时长，会把失败变成永不结束的等待；纯指数、不加随机性，仍可能让客户端同步重试。

### 31. API 速率限制：规定一段时间内允许多少请求

**是什么**：按用户、租户、IP 或接口限制请求速率，用于保护资源和分配配额。常见算法有固定窗口、滑动窗口、令牌桶等。

**Java 场景**：单实例可用 Bucket4j 等方案；多实例共享配额时，常在网关或 Redis 中以原子操作统一计数。超过限额时可返回 HTTP 429，并按协议提供重试提示。

**容易踩坑**：固定窗口在边界处可能出现突发流量。每台机器各限制 100 次，不等于集群总共 100 次。速率限制也不等于并发限制：慢请求仍可能长期占住大量资源。

### 32. 背压：处理不过来时，让上游减速或拒绝新工作

**是什么**：下游有容量边界，就需要把这个边界传回上游，避免任务无限积压。

**Java 场景**：线程池配置有界队列与明确拒绝策略；消费者限制拉取量和预取量；Reactor 等响应式链路可以通过需求信号协调速度。

**容易踩坑**：无界队列只是把过载变成高延迟和内存耗尽。`CallerRunsPolicy` 会让提交线程承担工作，某些场景可减速上游，但不能随意用在事件循环或必须快速响应的线程上。

### 33. 断路器：依赖持续失败时，暂时停止调用

**是什么**：根据失败率、慢调用比例等指标，把依赖调用切换到快速失败或降级，减少无效请求与资源占用。

**Java 场景**：通过 Resilience4j 为某个支付或物流依赖配置断路器。典型状态为 Closed（允许调用）、Open（拒绝调用）、Half-open（少量试探）。

**容易踩坑**：断路器通常不能自动终止一个已经卡住的网络请求，必须另外配置客户端超时。它也不等于限流器或并发隔离器；下单失败时不能为了“降级”返回虚假的支付成功。

### 34. 断路器恢复策略：用有限探测决定是否恢复流量

**是什么**：Open 状态等待一段时间后，进入 Half-open，允许有限数量的请求探测；满足成功条件后关闭，否则重新打开。

**Java 场景**：根据依赖的恢复特征配置等待时间、探测数量、统计窗口、最小样本数、失败阈值与慢调用阈值，并观察实际状态变化。

**容易踩坑**：恢复时间太短、探测量太大，会把刚恢复的服务再次压垮。每个实例通常各自维护断路器，集群探测总量可能更高；必要时配合随机等待和逐步放量。恢复策略是断路器的一部分，但值得单独设计。

![断路器状态转换：关闭时正常调用，达到失败阈值后打开，等待后半开探测，成功则关闭，失败则重新打开](/images/java-backend-50/circuit-breaker.svg)

*图 3：“关闭”表示允许请求通过，“打开”表示切断调用；恢复依赖有限探测。*

## 六、服务部署后，怎样承载流量和定位故障

### 35. 连接池：重复利用有限的昂贵连接

**是什么**：数据库连接建立有成本，连接池维护一组连接，调用者借出、用完归还。Spring Boot JDBC 应用中常见 HikariCP。

**Java 场景**：连接应及时关闭，JDBC 可用 try-with-resources；在池化数据源中，`close()` 通常表示归还连接。事务期间，连接往往会持续被占用。

**容易踩坑**：池越大不一定吞吐越高。20 个实例、每个池 30 个连接，可能消耗 600 个数据库连接。等待取连接超时与 SQL 执行超时是不同问题；慢事务和连接泄漏都能耗尽连接池。

### 36. 反向代理：站在服务前面接收并转发请求

**是什么**：客户端访问统一入口，由 Nginx、Envoy 或网关转发到后端，还可承担 TLS 终止、路由、请求大小限制等工作。

**Java 场景**：外部访问 `https://example.com/api/orders`，代理转发给内部 Spring Boot 服务。代理与应用需要协调超时、上传大小和可信转发头配置。

**容易踩坑**：不能直接信任任意客户端传来的 `X-Forwarded-For`。应由可信代理清理、设置转发头，否则 IP 限流、日志和安全判断可能被伪造。

### 37. 负载均衡：把请求分配给多个实例

**是什么**：用轮询、最少连接、加权等方式，把流量分散到可用后端。反向代理可以同时承担负载均衡，但两者不是同一个概念。

**Java 场景**：三个无状态 Spring Boot 实例共同提供订单 API，用户会话存到共享存储，或使用合适的无状态认证机制。

**容易踩坑**：增加实例却继续把关键状态存在单个 JVM 内，请求落到另一台就可能出错。长连接、粘性会话、健康检查与自动重试也会影响实际流量分布。

### 38. 健康检查：区分“还活着”和“可以接流量”

**是什么**：liveness 用于判断进程是否需要重启；readiness 用于判断实例当前能否接收新请求；startup 可为慢启动提供单独窗口。

**Java 场景**：使用 Spring Boot Actuator，并结合运行环境配置相应探针。readiness 失败通常意味着暂时从可用后端中移除。

**容易踩坑**：把所有外部依赖放进 liveness，数据库短暂故障就可能触发所有应用不断重启。readiness 是否依赖数据库，也要结合服务能否降级提供有效响应判断。

### 39. 优雅关闭：先停止接新活，再完成手头的工作

**是什么**：部署或缩容时，给进行中的请求和任务一个有边界的收尾机会。

```properties
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s
```

**Java 场景**：应用退出时配合流量摘除，Web 请求在宽限期内结束；消息消费者停止拉取，对未完成任务不确认或按协议交还；自建线程池也要正确关闭。

**容易踩坑**：平台终止宽限期必须给应用留下足够时间，还要考虑流量摘除传播延迟。上述配置不能保证任意后台线程都自动完成；超时强杀和崩溃仍需依靠幂等、持久化与恢复机制兜底。

### 40. 水平扩展 vs 垂直扩展：增加机器数量，还是增强单机

**是什么**：垂直扩展是给实例增加 CPU、内存等资源；水平扩展是增加实例或节点数量。

**Java 场景**：把 JVM 所在容器从 2 核 4GB 提到 4 核 8GB，属于垂直扩展；从 2 个应用副本增加到 6 个，属于水平扩展。

**容易踩坑**：业务瓶颈若在数据库锁或第三方接口，增加应用副本可能反而增加争抢。扩容前先量出瓶颈，并评估连接总量、状态共享、任务重复和下游容量。

### 41. 分布式追踪：把跨服务调用串成一次请求的路径

**是什么**：用 trace 表示整条调用链，用 span 表示其中一次 HTTP、SQL 或消息处理操作，通过上下文传播关联它们。

**Java 场景**：使用 OpenTelemetry 或 Micrometer Tracing，把网关、订单、支付调用和数据库操作关联起来，并在日志中带上 trace ID，定位延迟发生在哪一段。

**容易踩坑**：线程池、`@Async` 和 MQ 都可能成为上下文断点，需要正确传播。采样会影响能看到的链路；trace、日志和指标应互补，不能把支付信息等敏感数据随意放入 span 属性。

## 七、多个数据副本之间，怎样理解一致性

### 42. 读副本：把部分读请求交给复制出来的数据库

**是什么**：主库处理写入，副本接收数据变更并提供查询，分担读流量。某些系统还有其他复制拓扑，这里讨论常见主从场景。

**Java 场景**：订单历史列表可考虑读副本；刚下单后的结果确认、库存裁决等关键操作通常要按一致性要求读取主库或采用其他保障。

**容易踩坑**：`@Transactional(readOnly = true)` 通常表达只读意图，并不会自动配置主从路由。路由需由数据源或中间件实现，事务中途切换数据源也有边界。

### 43. 复制延迟：主库已更新，副本还没跟上

**是什么**：变更从主库传输并应用到副本需要时间，异步复制下副本可能暂时返回旧数据。

**Java 场景**：订单创建成功后立即查详情，却显示不存在。可以对关键读走主库，或在数据库支持时等待副本达到指定日志位置。

**容易踩坑**：“写后两秒内都读主库”只是经验策略，不能保证延迟永远小于两秒。应监控实际复制进度；异步复制下故障切换还可能涉及尚未复制的已确认写入。

### 44. 最终一致性：允许短暂不同，要求最后收敛

**是什么**：不同组件或副本可以暂时不一致，但在不再有新更新、传播和修复正常推进时，最终收敛到业务定义的一致状态。

**Java 场景**：订单提交后，积分稍后到账，搜索索引稍后更新。页面可以明确展示“处理中”，后台通过重试和对账补偿保证推进。

**容易踩坑**：“迟早会一致”不能代替设计。要定义允许多长延迟、怎样观测积压、失败由谁补偿。余额扣减或防超卖不能随便用最终一致性带过；还需要明确的约束、预留或协调方案。

### 45. 分布式事务：一次业务跨越多个独立资源

**是什么**：订单库、库存服务、账户服务分别管理自己的状态，一次业务需要协调它们的结果，单个本地事务覆盖不了全部资源。

**Java 场景**：强协调可以评估 XA/两阶段提交及其资源支持；跨服务长流程常考虑 Saga（多个本地事务加补偿）或 TCC（预留、确认、取消）。选型取决于一致性、可用性和业务可补偿性。

**容易踩坑**：Saga 补偿不是数据库回滚，退款也不是让现实中的扣款从未发生。补偿同样会失败，需要重试和人工处理。Outbox 适合可靠传播事实，但不自动让多个数据库同时原子提交。

## 八、系统持续演进，怎样不影响正在使用的人

### 46. 数据库迁移：把结构变更做成可追踪的版本

**是什么**：用版本化脚本维护建表、加列、约束和数据变更，常见 Java 工具有 Flyway、Liquibase。

**Java 场景**：通过 `V2__add_order_source.sql` 增加订单来源字段，并让环境按约定执行。脚本要与应用版本兼容，部署前评估锁、执行时长和数据规模。

**容易踩坑**：已经执行的版本脚本通常应保留原样，通过新脚本修正。生产环境不要只靠 Hibernate `ddl-auto=update` 管理结构演变；失败恢复、备份和数据修复也需提前规划。

### 47. 零停机迁移：让新旧版本在过渡期都能工作

**是什么**：通过兼容的分阶段变更，尽量维持服务可用，常用思路是 expand → migrate → contract。

**Java 场景**：把 `full_name` 拆成两个字段时，可按以下顺序推进：

1. 增加可空新列，旧应用继续工作。
2. 发布兼容版本，定义新旧字段的读写规则。
3. 分批回填历史数据，并处理回填期间的并发写入。
4. 校验数据，逐步切换读取逻辑。
5. 确认旧实例退出、回滚窗口结束，再删除旧字段。

**容易踩坑**：给大表加约束、索引或默认值是否锁表，取决于产品、版本和操作方式。“零停机”是设计目标，不代表所有 DDL 都没有等待；生产前要按真实规模验证。

### 48. 事件驱动架构：通过已经发生的事实连接业务模块

**是什么**：订单创建后发布 `OrderCreated`，积分、通知等模块订阅并作出反应。事件描述事实；命令表达“请执行某件事”，两者职责不同。

**Java 场景**：事件可以带事件 ID、聚合 ID、版本、发生时间和必要载荷。消费者独立演进，发布方不必同步等待所有后续动作。

**容易踩坑**：异步后会引入乱序、重复、协议演进和排查难题。Spring 的进程内 `ApplicationEvent` 本身不是持久消息系统，服务崩溃后的可靠交付需要额外机制。

### 49. CQRS：让写入模型与查询模型各自服务自己的需求

**是什么**：Command Query Responsibility Segregation，把修改状态的命令路径与读取状态的查询路径分开。它不要求一开始就拆成两个数据库。

**Java 场景**：下单命令围绕库存、金额和状态规则处理；订单列表查询直接读取适合展示的 DTO 或汇总表。规模增大后，再考虑用事件维护独立读模型。

**容易踩坑**：独立读模型通常会带来同步延迟与重建问题。普通 CRUD 没有复杂读写差异时，未必需要引入整套 CQRS；CQRS 也不要求使用事件溯源。

### 50. 事件溯源：把事件序列作为事实来源

**是什么**：保存 `OrderCreated → OrderPaid → OrderCancelled` 等事件，通过折叠事件恢复当前状态，而不只是覆盖当前状态字段。

**Java 场景**：订单聚合加载事件流后恢复状态，校验命令，再追加新事件。追加时携带预期流版本，防止两个请求基于同一旧版本同时写入；快照可以减少重放成本。

**容易踩坑**：“订单表加一张操作日志表”通常不等于事件溯源。历史事件结构演进、读模型重建、敏感数据治理都更复杂。重放构建状态时，也不能再次触发真实扣款或邮件等外部副作用。

## 把 50 个概念放回一次下单流程

![下单流程全景：网关进入订单服务，数据库提交库存订单与 Outbox，消息队列交给 worker，缓存辅助查询，Webhook 验签后入站](/images/java-backend-50/order-flow.svg)

*图 4：同步事务先保证本地正确性，异步链路再推动后续工作；实际系统可按需要拆分组件。*

理解单个名词之后，可以再沿着请求走一遍：

1. **进入系统**：反向代理接收请求，负载均衡选择实例，限流与并发控制保护容量，分布式追踪串起调用。
2. **执行下单**：通过连接池访问数据库，用参数校验、唯一约束、条件扣减和事务保证本地状态正确。
3. **传播结果**：订单与 Outbox 事件一起提交，由投递器发到消息队列，worker 幂等消费，失败时有限重试或进入死信。
4. **处理支付**：Webhook 先验签、校验业务信息、可靠落盘，再由处理器幂等推进状态，并容忍重复与乱序通知。
5. **提供查询**：结合索引、查询优化和必要缓存提供列表；读副本和异步读模型要向业务解释清楚延迟边界。
6. **应对故障与发布**：用超时、背压、退避和断路器控制失败扩散，通过健康检查、优雅关闭和兼容迁移持续演进。

这里没有要求一个小项目一开始就配齐全部组件。先把单体应用中的数据约束、事务和幂等做好，再根据观测到的瓶颈引入缓存、队列、读副本或分片，学习成本也更可控。

## 动手学习：用五个实验验证理解

只读概念容易产生“我懂了”的错觉。可以搭一个 Spring Boot + PostgreSQL 项目，按需增加 Redis 和消息队列，并做下面这些实验。

| 实验 | 操作 | 观察什么 |
| --- | --- | --- |
| 防超卖 | 库存设为 10，并发提交 100 次购买 | 成功订单不超过 10，库存不为负；订单与库存一致 |
| 防重复 | 用同一个请求 ID 并发提交，再用不同参数复用它 | 只产生一次业务效果，不同参数被拒绝或报告冲突 |
| 查 N+1 | 准备 100 条订单，访问关联客户信息 | 统计 SQL 数量，比较投影或批量加载后的变化 |
| 模拟投递崩溃 | 在发消息后、更新 Outbox 状态前停止进程 | 恢复后允许重复发送，但消费者只产生一次业务效果 |
| 模拟下游故障 | 让下游超时或持续返回 503 | 并发、队列长度、重试次数保持有界，断路器能探测恢复 |

随后再尝试热点缓存同时失效、Webhook 乱序到达、数据库迁移时新旧应用并行运行。每次都先写清楚“什么结果算正确”，再看系统是否满足它。

这些术语背后反复出现的是同一组问题：数据由谁裁决，操作能否重复，资源有没有上限，失败后如何恢复。能用自己的 Java 代码复现一次、解释一次，再修好一次，概念才会逐渐变成解决问题的能力。
